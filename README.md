## Вопросы
1. Что такое репозиторий?
Репозиторий — это папка проекта вместе с историей всех изменений. В нём хранятся: файлы проекта, информация о коммитах, ветках и т. д., история изменений (коммиты).

2. Чем локальный репозиторий отличается от удаленного?
Локальный репозиторий — копия проекта на вашем компьютере. Вы работаете с ним напрямую в VS Code, создаёте коммиты, переключаетесь между ветками.

Удалённый репозиторий — общая копия проекта в сети. Он служит для: резервного копирования кода, совместной работы команды, развёртывания проекта.

3. Что делает команда Pull?
Команда pull загружает изменения из удалённого репозитория и сразу применяет их к текущей ветке.

4. Что делает команда Push?
Команда push отправляет ваши локальные коммиты в удалённый репозиторий. После Push другие участники команды могут увидеть ваши изменения.

5. Чем Fetch отличается от Pull?
fetch — только скачивает изменения из удалённого репозитория, но не применяет их к вашей локальной ветке. Вы можете посмотреть, что изменилось, прежде чем объединять. pull — скачивает и сразу объединяет изменения с текущей веткой.

6. Что такое ветка?
Ветка — независимая линия разработки внутри репозитория. Она позволяет работать над новой функцией, не затрагивая основной код, исправлять ошибки в отдельной ветке, тестировать экспериментальные решения. Основная ветка называется main.

7. Почему не всегда удобно работать сразу в main?
Потому что работа напрямую в main повышает риск сломать рабочий код, затрудняет параллельную разработку нескольких функций, усложняет откат изменений, мешает проведению код‑ревью. Лучше создавать отдельные ветки для каждой задачи.

8. Что такое Pull Request?
Pull Request — запрос на объединение изменений из одной ветки в другую (обычно в main). Это не просто техническая операция, а процесс согласования - вы предлагаете изменения, другие разработчики их проверяют, при необходимости вносятся правки, после одобрения изменения вливаются в основную ветку.

9. Зачем нужна проверка Pull Request другим участником?
Чтобы выявить ошибки до их попадания в основной код, улучшить качество кода, поделиться знаниями в команде, убедиться, что изменения соответствуют задачам проекта.

10. Что такое merge conflict?
Merge conflict — ситуация, когда Git не может автоматически объединить изменения из‑за противоречий в коде.

11. Почему возникает merge conflict?
Когда два разработчика изменили одну и ту же строку в разных ветках, один удалил файл, а другой его отредактировал, изменения пересекаются в одном участке кода.


12. Как понять, какой вариант кода оставить при конфликте?
Нужно открыть файл с конфликтом в VS Code — редактор подсветит проблемные места и решить, какой вариант оставить (или объединить оба).

13. Что будет, если забыть сделать Pull перед началом работы?
Если не выполнить git pull, то вы начнёте работать со старой версией кода, при попытке Push возникнет ошибка — Git не позволит перезаписать чужие изменения, придётся сначала выполнить Pull, разрешить возможные конфликты, и только потом отправлять свои изменения.

14. Почему коммиты должны быть маленькими и понятными?
Потому что они упрощают поиск ошибок (легко отследить, какой коммит что сломал), меньше кода для проверки, позволяют точнее описывать изменения в сообщениях коммитов, дают возможность безопасно откатывать отдельные изменения.

15. Что было самым сложным в этой практической работе?
Самым сложным было создание конфликта с PR.
